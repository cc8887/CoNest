# 微信、飞书和 QQ 的开源统一接入方案

核查日期 2026-11-21。这里的微信指普通微信里的 ClawBot / iLink。QQ 指 QQ 开放平台机器人。企业微信、公众号和使用个人 QQ 账号的 OneBot 属于各自独立的渠道。以下结论来自官方文档、适配器源码，以及一次本地消息映射检查。真实账户的三渠道联调待验证。

## 群消息的可见范围

- **飞书**。无 @ 的消息要求应用取得 `im:message.group_msg`，并订阅相应的群消息事件。`requireMention` 决定收到后是否响应。CoNest 当前的智能寻址据此先核对平台 @、回复和同话题待答，再做语义判断。[OpenClaw 飞书权限说明](https://docs.openclaw.ai/channels/feishu/access-control) · [CoNest 智能寻址](architecture.md#智能寻址)
- **官方 QQ**。`GROUP_AT_MESSAGE_CREATE` 表示消息 @ 了当前 Bot。已经开启「接收所有消息」的机器人可以通过 `GROUP_MESSAGE_CREATE` 收到非 @ 群消息。腾讯维护的 Node SDK 和 Octop QQ 适配器都识别这两个事件。有无全量接收权限和真实群实际推送字段，仍要用目标应用核验。QQ群 `member_openid` 与 C2C 私聊的 `user_openid` 分属各自的事件字段，条件性返回的 `union_openid` 需核验作用域后才能用于关联。引用索引 `ref_msg_idx` 和用于被动回复的消息 `id` 应分别保留。[腾讯 QQ 全量事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html) · [群 @ 事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_at_message_create.html) · [C2C 事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html) · [Node SDK 分派](https://github.com/tencent-connect/qqbot-nodejs/blob/429a0f1b798f3b0fcef3679e207dbc0469a1df2d/src/protocol/gateway/event-dispatcher.ts#L237-L260) · [Octop QQ 解析](https://github.com/TencentCloud/octop-gateway/blob/f7b419dc61e62b1387ed8196e94d572097662f75/src/octop_gateway/channels/qq/channel.py#L1070-L1171)
- **普通微信**。腾讯 OpenClaw 插件仍声明 `chatTypes: ["direct"]`。Octop 的微信适配器也按 `from_user_id` 建立收发地址。现有证据支持 ClawBot 私聊，普通微信群仍需要受支持的事件来源及真机验证。[腾讯微信插件源码](https://github.com/Tencent/openclaw-weixin/blob/ffc7ae1686e84da944579af37f4fbef522183688/src/channel.ts#L233-L243) · [Octop 微信入站源码](https://github.com/TencentCloud/octop-gateway/blob/f7b419dc61e62b1387ed8196e94d572097662f75/src/octop_gateway/channels/weixin/channel.py#L770-L785)

## 对 CoNest 的取舍

如果近期目标是**在已有微信和飞书基础上补齐 QQ**，建议优先用腾讯官方 Node SDK 编写独立 QQ Source，复用现有工单队列和 outbox。首期验证 QQ 私聊、群 @、同消息重投去重和原会话回复，再用有全量授权的群验证无 @ 寻址。QQ 现行文档列出的单聊、群聊被动回复有效期均为 60 分钟，有独立的主动发送规则。超过回复窗口的工单结果、定时任务通知和用户主动推送设置需要分别验收。[腾讯 Node SDK](https://github.com/tencent-connect/qqbot-nodejs) · [QQ 现行消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html) · [CoNest 渠道注册](../../cordis.patch.yml)

如果目标是**让多种 IM 长期共用一套接入层**，优先验证 Octop Gateway 作为消息收发进程。OpenClaw 适合按完整应用部署或用于对照三渠道行为，它的默认私聊路由可汇入同一 Agent Session。把 OpenClaw 用于 CoNest 时，需要用插件接管消息并显式验证租户和回传地址。[Octop 处理器接口](https://github.com/TencentCloud/octop-gateway/blob/f7b419dc61e62b1387ed8196e94d572097662f75/README.md#unified-message-abstraction) · [OpenClaw 会话路由](https://docs.openclaw.ai/channels/channel-routing#session-key-shapes-examples)

CoNest 的 `src/ingress/messages.ts` 已有网关形状的映射，但仍需对接真实字段。本地用 Octop 源码形状构造 QQ 群事件时，`msg_id` 未映射会被现有适配器拒绝。补上 `message_id` 后可以生成 Trigger，现有映射仍会丢弃 @ 和引用字段，并用本地时间替代平台时间。桥接要保留渠道实例、发送者及类型、会话、原消息及引用 ID、平台时间和提及。CoNest 按验证过的成员绑定决定工单归属，通用网关回传当前只允许原私聊。群回传需走该 Source 独立的群授权规则。[CoNest 入站和回复映射](../../src/ingress/messages.ts#L205-L228) · [成员身份边界](architecture.md#飞书群聊主体识别) · [Octop QQ 字段](https://github.com/TencentCloud/octop-gateway/blob/f7b419dc61e62b1387ed8196e94d572097662f75/src/octop_gateway/channels/qq/channel.py#L1098-L1169)
